# 相机死区 + 弹性跟随

本文档记录 `gdexample` 当前相机跟随实现的做法和原理。这里描述的是本仓库现有代码，不是所有俯视角游戏的通用实现。

涉及文件：

| 文件 | 职责 |
| --- | --- |
| `src/base/ICamera.h:77-114` | 跟随参数与 `Follow()` 声明、状态成员 |
| `src/base/ICamera.cpp:14-88` | 死区裁剪与阻尼逼近算法 |
| `src/game/Game.cpp:215-221` | 绑定跟随目标、手感参数 |
| `src/game/Game.cpp:310` | 每帧调用入口 |
| `src/camera/Camera.cpp` | SPX ABI 薄封装，只提供读/写相机位置 |

## 1. 要解决的问题

原始写法每帧无条件执行：

```cpp
GetCamera()->SetPosition(gd_sprite->GetPosition());
```

它的含义是"相机中心恒等于人物位置"，于是人物在屏幕上永远居中，视觉上是世界在滑动，而不是人在走。

关键点：**加平滑解决不了这个问题**。平滑只改变到达目标的过程，不改变目标本身。目标是人物的位置，收敛终点就一定是屏幕正中。要让人物偏离中心，必须改目标点的定义。

## 2. 核心原理：把等式改成约束

```text
等式（原来）： cam ≡ player            偏移恒为 0      → 永远居中
约束（现在）： |player − cam| ≤ H       区内保留自由度  → 可以偏离中心
```

其中 $H$ 是死区半幅。相机的职责不再是"到达人物的位置"，而是"让人物的屏幕偏移保持在允许区间内"。区间内相机完全不动，区间外相机只补足**超出的那一段**。

```text
              屏幕（可见世界 960×540）
      ┌─────────────────────────────────┐
      │          死区 480×189            │
      │      ┌───────────────────┐      │
      │      │          ★ 人物    │      │   区内走动 → 相机不动
      │      │   屏幕中心         │      │   跨出边界 → 相机开始追
      │      └───────────────────┘      │
      └─────────────────────────────────┘
```

## 3. 每帧五步流水线

对应 `ICamera::Follow(float delta)`：

```text
① 读回相机当前位置 cam          引擎实际值，不是自己记的状态
② 计算误差 err = player − cam   人物相对屏幕中心偏了多少
③ 死区裁剪 r = PullBackToRange(err, H)
                                区内返回 0；区外只返回超出量
④ 目标 wanted = cam + r         相机只需走这么点
⑤ 阻尼逼近 cam += (wanted − cam) × (1 − e^(−k·dt))
```

第 ③ 步是整个手感的根。它返回的不是"到人物的距离"，而是"越界的距离"：

```cpp
float PullBackToRange(float offset, float half)
{
    const float distance = std::fabs(offset);
    if (distance <= half) return 0.0f;              // 区内：相机不动
    return offset > 0.0f ? distance - half
                         : half - distance;         // 区外：只补超出量
}
```

所以相机从来没有"把人拉回正中"的意图，它只在越界时把人物卡回边界。

## 4. 四个设计点及其理由

### 4.1 稳态落在死区边缘，且不可能过冲

设人物位置 $P$、相机位置 $C$、误差 $e = P - C$。相机运动速率正比于超出量：

$$\dot C = k\,\big(|e| - H\big)\,\mathrm{sgn}(e) \quad (|e| > H)$$

系统收敛到 $|e| = H$ 处，并且只能从**外侧**逼近：$|e|$ 一旦不大于 $H$，驱动力立刻归零。因此：

- 人物停下后，最终停在死区边缘，而不是屏幕中心；
- 人物不会被甩过中心跑到另一侧。这是超出量表述保证的数学性质，不需要额外的边界判断。

### 4.2 为什么必须带阻尼

如果第 ⑤ 步直接把 $r$ 加上去（$k \to \infty$），会有两个毛病：

1. **加速度不连续**。人物一跨出边界，相机速度瞬时从 0 跳到人物速度；跨回来时又瞬时归零，画面表现为"猛地一抽"。阻尼把阶跃变成斜坡。
2. **物理抖动直通画面**。玩家精灵是 `PhysicsMode::Dynamic`，`move_and_slide()` 结算出的坐标每帧存在微小抖动，硬补会把抖动 1:1 传给相机。$1 - e^{-k\,dt}$ 是一阶低通，滤掉高频分量。

一阶指数逼近不会振荡，所以"弹性"指的是起停柔顺，不是果冻回弹。

### 4.3 为什么每帧读回引擎实际位置

第 ① 步读 `GetPosition()` 而不是自己累加状态，使跟随成为**闭环**：

- 相机边界限制（`SetCameraLimit`）把相机夹住后，下一帧读回来就是夹住后的值，不会出现"我们以为相机在 A、实际在 B"的累积漂移；
- 外部直接移动相机（过场、震屏）会被跟随逻辑自然接住，从新位置继续收敛；
- 引擎自带平滑（`SetCameraSmoothing`）因此变成可选项，而不是隐式依赖。

### 4.4 为什么死区用比例而不是世界坐标

可见世界尺寸为：

$$W_{\text{可见}} = \frac{W_{\text{视口像素}}}{z} \qquad H_{\text{可见}} = \frac{H_{\text{视口像素}}}{z}$$

死区半幅取 $H = \tfrac{1}{2} W_{\text{可见}} \times \text{ratio}$，因此**缩放镜头时死区在屏幕上始终是同一大小**。若写成固定世界坐标，`zoom` 一变，死区相对屏幕的比例就跟着变，手感随缩放漂移。

兜底行为：

- `GetZoom()` 拿不到值（函数指针为空返回 `{0,0}`）→ 按 $z = 1$ 处理；
- `GetViewportRect()` 拿不到值 → $H = 0$，退化为等式跟随，即原行为，不会失控。

## 5. 参数与量化手感

参数只有两个，都在 `Game.cpp:220-221`：

```cpp
mData->camera->SetFollowDeadzone(XVec2{0.5f, 0.35f});  // 比例，非像素
mData->camera->SetFollowDamping(6.0f);                 // ≤0 表示不做平滑，瞬时补齐
```

人物匀速跑动达到稳态时（$v$ 为人物速度，$k$ 为 damping）：

| 量 | 公式 | 当前数值（960×540、$z=1$、$v=200$、$k=6$） |
| --- | --- | --- |
| 死区半幅 $H_x$ | $\tfrac{1}{2} W_{\text{可见}} \cdot \text{ratio}_x$ | 240 px |
| 死区半幅 $H_y$ | $\tfrac{1}{2} H_{\text{可见}} \cdot \text{ratio}_y$ | 94.5 px |
| 人物稳定偏移 | $H + v/k$ | 240 + 33 ≈ 273 px（X 轴） |
| 相机稳态速度 | 收敛到 $v$ | 与人同速 |
| 时间常数 | $1/k$ | 0.17 s |
| 收敛耗时（≈95%） | $3/k$ | 0.5 s |

$H + v/k$ 这一项说明 **damping 不只决定"追得多快"，还决定"跑动时人被甩开多远"**。

调参对照：

| 想要的效果 | 改动 |
| --- | --- |
| 相机更懒、画面更稳 | 死区比例调大，例如 `{0.6f, 0.45f}` |
| 更跟手、人物偏移更小 | damping 调大，例如 `10 ~ 12`；或死区调小 |
| 某个轴完全跟随（例如横版只留 X 死区） | 该轴比例填 `0` |
| 起步/停步毫无缓动 | damping 填 `0`（等价于瞬时补齐） |

死区比例 `{0.25f, 0.25f}` 对应全区 240×135，比当前默认小一圈，画面明显更跟手。

## 6. 分层结构

```text
Game::OnEngineUpdate      只调用 GetCamera()->Follow(ddelta)
        ↓
ICamera::Follow           死区裁剪 + 阻尼逼近 + 跟随参数状态
        ↓ 只用四个抽象调用：GetPosition / SetPosition / GetViewportRect / GetZoom
        ↓
Camera (具体实现)          SPX ABI 薄封装，不含任何玩法逻辑
        ↓
spx_api::camera_*         引擎导出接口
```

算法挂在接口基类上，是因为它只依赖上面四个抽象调用，不依赖 SPX 签名。以后 ABI 变更不会波及手感逻辑。

两个附带约定：

- `SetFollowSprite` 保存的是 `wptr<ISprite>`，人物销毁后 `lock()` 返回空，跟随自动失效；
- 绑定时调用 `SetCameraSmoothing(false)`：引擎自带平滑与 `Follow` 的阻尼会串成两段延迟，表现为又黏又飘。平滑统一由 `Follow` 负责。

`Follow` 在 `delta <= 0`、跟随目标为空、或目标尚无 `IGdSprite` 时直接返回，不写相机。

## 7. 已知取舍

**人物停下后永久停在死区边缘，不会回中。** 一直往右走再停下，人物就常驻在中心右侧约 273 px 处。这正是"一般游戏"的观感，也是本节要显式记录的代价。

如果需要"静止若干秒后缓缓回中"（idle recenter），扩展点在 `ICamera::Follow` 第 ④ 步之后：维护一个静止计时器，超过阈值时把目标从"边缘"改为按一个更小的阻尼系数缓慢移向 $H=0$。它不改变死区语义，只是让边界随空闲时间收缩。

同理，前瞻偏移和固定取景也都可以叠加在第 ④ 步：`wanted = cam + r + bias`，其中 $bias$ 取人物朝向、速度或常量偏移。当前实现刻意只保留死区一项，避免多个来源同时影响落点、导致手感无法归因。
